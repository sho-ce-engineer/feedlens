# ADR-0005: Hotでない判定には、カテゴリと点数を持たせない

- 状態: 採用(PR #54 でマージ済み)
- 日付: 2026-11-28

## 背景

PR #54 の最初の実装では、Hot でない記事の判定にも `category: "tech"`、`score: 1` を入れていた(Gemini のスキーマで両方を必須にした都合)。レビューで、「後の分析のときにノイズになる可能性が残る」という指摘があった。

## 決定

- 判定結果の型を、`{ isHot: false }` と `{ isHot: true, category, score }` のどちらかにする。
- Gemini の応答スキーマでは、`category` と `score` を任意の欄にし、必須は `isHot` だけにする。
- 応答を判定結果に変える処理(`toJudgement`)で、次を守る。
  - `isHot: true` なのに `category` か `score` が欠けていたら、判定失敗として扱う。
  - `isHot: false` で `category` や `score` が付いていても、捨てる。
- プロンプトでは、`isHot` が false のときは `category` と `score` を出力しないよう指示する。
- 通知する記事の点数(`ClassifiedArticle.score`)は、1〜10の整数に型で絞る。

## 検討した代替案

- Hot でない記事用に、別のカテゴリ(`none` など)を作る: カテゴリの値が増え、カテゴリごとに処理する箇所すべてに影響する。
- `tech` と `score: 1` の仮の値を入れ続ける: 分析のときに、tech の偏りとして混ざる。

## 結果

- Hot でない判定に、意味のない値が入る余地がなくなった。
- 判定結果を将来保存して分析する場合(リアクションのフィードバックなど)に、そのまま使える。

## 未確認と見直しの条件

- Gemini の構造化出力が、任意の欄を指示どおり省略するか、実際には確かめていない(作業場の VM は外に通信できない)。省略しない場合でも、`toJudgement` が捨てるので動作は変わらない。`isHot: true` で欄が欠ける頻度が高い場合は、プロンプトかスキーマを見直す。
