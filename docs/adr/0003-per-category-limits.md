# ADR-0003: 通知の上限をカテゴリ別に設け、省略件数をサマリに出す

- 状態: 採用(PR #54 でマージ済み)
- 日付: 2026-11-28

## 背景

通知の件数に上限がなく、読み切れない量になっていた。ジュニアエンジニア向けの技術記事と、ガジェットなどの製品紹介・レビューでは、点数の付き方が違う。同じ順位表に混ぜると、片方がもう一方に埋もれやすい。

## 決定

- 通知は、カテゴリごとに上限まで。技術記事(`tech`)は15件、製品・ガジェット(`product`)は5件(合計20件)。上限は `categoryLimits` に置く。
- カテゴリごとに見出しを付けて、見出し → 記事の順で送る。記事が無いカテゴリは見出しも送らない。
- 一方のカテゴリで枠が余っても、もう一方には回さない。
- 製品・ガジェットの範囲は、「ガジェット、PC・周辺機器、サービスの製品紹介やレビュー」とする。
- 上限で省略した件数を、カテゴリごとに実行結果サマリに出す。Hot の候補の半数を超えて省略されたカテゴリには、判定基準や上限の見直しを促す警告を付ける。
- 判定・要約は、カテゴリを順に処理する。カテゴリを並列にすると、Gemini の同時呼び出し数が `GEMINI_CONCURRENCY` を超え、レート制限に当たるため。
- Discord への送信は、1件ずつ行う(レート制限のため。従来どおり)。

## 検討した代替案

- カテゴリを分けず、全体で20件に絞る: 製品記事が技術記事に埋もれる、またはその逆になる。
- 余った枠をもう一方に回す: 見出しと上限をカテゴリごとに分ける方針と合わない。

## 結果

- 「全体のうち、ちょっとだけ省略される」は想定の範囲、「大半が省略される」は見直しのきっかけ、という見方で、サマリを使う。
- 上限の数字(15と5)は、現時点の見込みで、実際の記事数から決めた値ではない。
- 警告の線「半数超」は、暫定の値。変えるときは `isMostlyCut` の1か所。

## 未確認と見直しの条件

- 実際の Hot の件数と、省略される割合は、まだ見ていない。マージ後のサマリで確かめる。
- 省略が常に半数を超える、または上限まで届かない日が続く場合は、上限と判定基準(`criteria.json`)を見直す。
